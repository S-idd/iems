## Run the CLI demonstration

From the IEMS repository:

```bash
python3 scripts/dcg/advisory_rehearsal.py --scenario all
DCG_AI_ENABLED=false python3 scripts/dcg/advisory_rehearsal.py --scenario all
python3 scripts/dcg/advisory_rehearsal.py --endpoint http://127.0.0.1:59999 --scenario all
python3 -m unittest scripts/dcg/test_advisory_rehearsal.py -v
```

The first command uses the installed package at `.dcg/runtime/dcg-4.0.0-rc.1-macos-arm64` by default, or `DCG_HOME`. It checks every contract with the packaged DCG CLI **before** starting its owned Rust process. It then attaches a separate advisory object and stops only that process. The second command starts no Rust process. The third uses an intentionally absent loopback endpoint and records `UNAVAILABLE`. A `--timeout-ms` option bounds each prediction. The wrapper has a 1 MiB request limit, 64 KiB response limit, no retry, strict label/seed/probability validation, and no arbitrary URL or model path from a response.

The output contains `governanceExitCode` (0 PASS, 1 FAIL), the final deterministic verdict, reason, source file hashes, canonical model input hash, advisory status, three raw seed predictions, artifact hashes, duration, and agreement. No raw schema is copied into evidence. `AGREES` means all three labels match SAFE for PASS or BREAKING for FAIL. Any other valid label set yields `DISAGREES`; it cannot alter the final verdict. The synthetic disagreement in `disagreement-test.json` is generated by a test-only monkeypatch and **is not a model prediction**. That adapter is not exposed as a CLI option or packaged runtime feature.

Actual local results: the optional enrollment field is PASS with three SAFE predictions. Changing enrollment `studentId` from integer to string is FAIL with three BREAKING predictions. Changing both that field and scholarship `amount` from number to string yields two independent FAILs, each with three BREAKING predictions. AI-disabled and absent-endpoint runs retain all verdicts. Unit tests additionally cover timeout, malformed output, and dropped connections for both PASS and FAIL through a loopback HTTP server. Test-only fault evidence is in separate `timeout-advisory.json`, `invalid-output-advisory.json`, and `crash-advisory.json` files.

The Java service now persists optional shadow inference against the completed deterministic run ID and displays it in the packaged check-detail dashboard. The synchronous `/demo/comparison` path is still separate and is not an enforcement gate. The Phase 2.1 launcher starts Java first and Rust best-effort. The IEMS breaking proposal still blocks dispatch if AI is unavailable. See the private `.dcg/rehearsals/phase2-ai-launcher-resilience-20260918/` evidence.

For Phase 2.2, set `DCG_HOME=/absolute/path/to/freshly-extracted/dcg-package` in IEMS. The service launch commands are `DCG_AI_ENABLED=true DCG_DATA_DIR=<isolated-state> "$DCG_HOME/bin/start"`, `DCG_DATA_DIR=<isolated-state> "$DCG_HOME/bin/status"`, and `DCG_DATA_DIR=<isolated-state> "$DCG_HOME/bin/stop"`; use the same absolute `DCG_DATA_DIR` for all three. `DCG_AI_ENABLED=false` remains deterministic-only. ## Phase 2.2 service architecture and API

`POST /checks` queues a run. The check runner compares schemas, stores the authoritative PASS/FAIL and compatibility logs, then publishes the existing deterministic failure notification. Only after that does it dispatch the bounded advisory observer. Flyway V13 adds `check_run_advisories` with `run_id` as the primary key and foreign key to `check_runs`; it has no update path to the deterministic status. The observer stores `AVAILABLE`, `UNAVAILABLE`, `TIMEOUT`, or `INVALID_OUTPUT`, its input hash, duration, model identity, mean per-label probabilities plus all three raw seed predictions when available, agreement, timestamps, and a test-only marker. Failed inference stores no label or probabilities. An advisory log uses `code=ai_advisory_completed`; deterministic logs remain separate. Existing V12/Phase 1 records migrate and remain readable with no advisory.

`GET /checks/{runId}` remains the original deterministic response and is backward compatible. `GET /checks/{runId}/advisory` returns the linked advisory, HTTP 204 when disabled or still pending, and HTTP 404 for an unknown run. Poll the advisory endpoint after the run reaches PASS/FAIL; the inference worker is asynchronous. `GET /checks/{runId}/logs` contains both the deterministic completion and later advisory event. `/ui/checks/{runId}` renders the deterministic decision first, then the visibly separate advisory panel. A test-only response is explicitly marked as such. The dashboard is a rendered Thymeleaf page, not a static fixture.

The model reports three frozen V9 seed outputs. The displayed label uses a majority vote; displayed probabilities are arithmetic means of the three seed scores. The raw seed outputs remain in the API record. The model artifact SHA-256 field identifies the pinned three-artifact set by hashing the concatenated pinned artifact digests; the Java client does not remotely attest the Rust endpoint. Probability calibration remains unverified. This model does not generate explanations, corrections, or remediation.

## Repeat the packaged service demo

From the IEMS root, while all launcher processes are stopped, prepare a fresh isolated state:

```bash
export DCG_HOME="/absolute/path/to/freshly-extracted/dcg-package"
export DCG_DATA_DIR=$(mktemp -d "$PWD/.dcg/rehearsals/phase2-service-advisory-$(date +%Y%m%d-%H%M%S)-XXXXXX")
mkdir -p "$DCG_DATA_DIR/contracts/iems.enrollment"
cp "$DCG_HOME/contracts/policy-packs.json" "$DCG_DATA_DIR/contracts/policy-packs.json"
cp contracts/iems.enrollment/metadata.yaml contracts/iems.enrollment/v1.json "$DCG_DATA_DIR/contracts/iems.enrollment/"
cp scripts/dcg/fixtures/compatible.json "$DCG_DATA_DIR/contracts/iems.enrollment/v2.json"
cp scripts/dcg/fixtures/breaking.json "$DCG_DATA_DIR/contracts/iems.enrollment/v3.json"
DCG_AI_ENABLED=true "$DCG_HOME/bin/start"
```

The launcher uses ports 8080/8081, generates a local password file under `DCG_DATA_DIR`, and keeps it out of the exported Postman environment. Set `dcg_base_url` to `http://127.0.0.1:8080`, `dcg_username` to `demo`, and `dcg_password` locally from that password file. Run the collection folder **Phase 2.2 — real service AI advisory**. Stop and restart Java against the same state, then run **Phase 2.2 — verify after service restart** with the saved run IDs. Open both `/ui/checks/{runId}` pages. For no-AI mode, stop first, then start with `DCG_AI_ENABLED=false`; status must show `Rust advisory process: STOPPED`.

The unavailable and controlled-fault scenarios require isolated endpoints and unique `commitSha` values so webhook deduplication does not hide independent events. `shadow.inference.test-only-adapter=true` is rejected unless the service uses the `phase2-rehearsal` profile; the normal packaged launcher fixes `local-demo`, so test-only injection is unavailable there. The test adapter response is marked `testOnlyAdapter: true` and does not claim a real model artifact. The separate **Phase 2.2 — verify existing fault runs** Postman folder verifies stored results without submitting more checks.
